# Универсальная партнёрская платформа JetSim — план реализации

> **Для исполнителя:** выполнять задача за задачей; чекбоксы `- [ ]` отмечать по ходу. Ничего не коммитить и не пушить — коммитит владелец.

**Цель:** центральный B2B-слой в `jetsim` (Reseller, баланс с резервами, B2B-заказы) + два новых проекта `jetsim-partner-backend` и `jetsim-partner-dashboard`.

**Архитектура:** деньги, тарифы компании и выпуск eSIM живут только в центральном JetSim; партнёрский backend (своя БД) хранит компании, сотрудников, ключи сайта, локальные заказы и синхронизируется с центром (каталог — при старте и раз в 5 мин, заказы — каждые 20 с). Центр отдаёт два набора методов: управляющие (`/b2b-admin/*`, ключ только у нас) и закупочные (`/b2b/*`, ключ конкретной компании).

**Стек:** NestJS 11 + Prisma 6 + PostgreSQL (оба backend), React/Vite/Tailwind (dashboard), jest + supertest, реальный Postgres во временном кластере (порт 54329) для миграций и конкурентных резервов.

**Спека:** ТЗ «Универсальная партнёрская платформа JetSim» из переписки (разделы 1–5).

## Глобальные ограничения (из ТЗ, дословно по смыслу)

- Валюта v1 — RUB; суммы — целые копейки; финансовая история неизменяема (исправления — новыми операциями).
- Роли: наш `SUPER_ADMIN` (без `company_id`), их `ADMIN` и `AGENT` (обязателен `company_id`). Матрица прав — раздел 2 ТЗ; все проверки на backend.
- Компанию определять по авторизации, не по присланному `company_id`; агент дополнительно ограничен автором заказа.
- Пользователей блокировать, не удалять. Агентам нет отдельных кошельков/комиссий/цен. Источник покупки: админ | агент | API-ключ сайта.
- Один заказ = одна eSIM; уникальность `(company, client_order_id)`; тот же запрос → тот же заказ, другой состав → конфликт (и в dashboard тоже).
- Резерв при покупке атомарно → списание после подтверждённой выдачи → освобождение один раз при достоверном отказе; таймаут/неизвестно → резерв держим до сверки, автоповтор покупки запрещён; баланс не уходит в минус при параллельных запросах.
- Каталог несёт `price_version`; заказ передаёт версию; расхождение → отказ «обновите каталог»; название/цена/срок фиксируются в заказе.
- Отмена суперадмином — до отправки поставщику; после — сверка и подтверждённый возврат.
- `/api/v1`: `GET /tariffs`, `GET /balance`, `POST /orders` (202), `GET /orders`, `GET /orders/:id`, `GET /orders/:id/esim`, `GET /orders/:id/usage`. Ключ сайта = компания, видит все её заказы; полное значение показывается один раз, хранится хеш; ключ не меняет баланс/цены/сотрудников/заказы-отмены. Агентских API-ключей нет.
- QR только через авторизованный endpoint; служебные ответы поставщиков и закупочная стоимость JetSim у поставщиков — только суперадмину.
- Нельзя переносить `.env`, клиентов, заказы, учётки JetSim; workflow не должен деплоить в `/var/www/jetsim`; ветка `main`; НЕ коммитить.

## Решения, которых нет в ТЗ (приняты мной)

- B2B-выпуск идёт через обычные строки `Sims` центрального JetSim (callback'и провайдеров находят их по тем же идентификаторам). Строка помечается `Sims.reseller_order_id`; `order_id = NULL`; `user_id` = служебный пользователь компании (`User.is_service = true`, создаётся вместе с Reseller). Розничные выборки (админ-список SIM, пользователи, дашборд) получают фильтр «не B2B / не служебный».
- Для B2B-sim файл QR не сохраняется в публичный `/uploads/qr` (перечислимый путь) — QR отдаётся только авторизованным методом, картинка генерируется на лету.
- Центр различает исход отправки поставщику: `REJECTED` (ответ поставщика с отказом или HTTP 4xx) → освобождаем резерв; `UNKNOWN` (таймаут/сеть/5xx) → `RECONCILE`, резерв держим, ping суперадмину в Telegram.
- Суммы в БД — `BigInt` (копейки), наружу — `number` (проверка `Number.isSafeInteger`).
- Резерв — условный `UPDATE … WHERE balance - reserved >= X` (одна строка счёта сериализует конкурентов) в одной транзакции с вставкой заказа и записью журнала; идемпотентность операций — `UNIQUE(reseller_id, idempotency_key)` в журнале.
- Закупочный ключ компании в центре хранится хешем; партнёрский backend хранит его зашифрованным (AES-256-GCM, ключ из env) и использует для закупочных вызовов этой компании. Управляющий ключ — только в env партнёрского backend и центра (хеш), в браузер не попадает.
- `activation_code` (LPA-строка) в партнёрской БД хранится зашифрованным; QR-PNG строится на лету.

## Review Focus (что ТЗ подразумевает, но легко пропустить)

1. Двойной клик / ретрай `POST /orders` с тем же `client_order_id` → один заказ, один резерв (тест на уровне центра и партнёрского backend).
2. N параллельных покупок при балансе на K<N заказов → ровно K резервов, баланс ≥ 0 (тест на реальном Postgres).
3. Таймаут провайдера после отправки → `RECONCILE`, резерв остаётся, повторной закупки нет; повторный callback → не двойное списание.
4. Блокировка компании: покупки 403, просмотр уже выданных eSIM работает; блокировка агента/отзыв ключа → мгновенный отказ.
5. Подстановка чужого ID (заказ, QR, сотрудник, отчёт, баланс) → 404 (а не 403 — не раскрываем существование).

- [ ] Проверка: `prisma validate`, `prisma generate`, `tsc --noEmit` без новых ошибок.

### Task A2: Денежный сервис `ResellerLedgerService`
**Files:** Create `src/modules/b2b/ledger/reseller-ledger.service.ts` + spec (интеграционный, `central_test`).
**Produces:** `reserve(tx, {resellerId, orderId, amount}): Promise<void>` (бросает `InsufficientFundsError`), `capture(tx, orderId)`, `release(tx, orderId)`, `topUp({resellerId, amount, comment, actor, idempotencyKey?})`, `adjust(...)` (±, не уводит available в минус), `refund(tx, orderId, comment)`, `getBalance(resellerId): {balance, reserved, available}`, `listLedger(resellerId, page)`.
- [ ] Тесты: параллельные `reserve` (20 запросов при балансе на 7) → ровно 7; повторный `capture`/`release` с тем же ключом — no-op; нельзя `release` после `capture`; ледгер неизменяем (UPDATE/DELETE запрещены триггером БД).
- [ ] Реализация: `$executeRaw` условный UPDATE; журнал хранит `balance_after`/`reserved_after`.

### Task A3: Управляющее API (`/b2b-admin/*`)
**Files:** Create `src/modules/b2b/admin/*` (`ManagementKeyGuard`, `ResellersAdminController`, сервисы).
**Produces:** создание/просмотр/блокировка Reseller (с служебным User и счётом), выпуск/отзыв закупочных ключей (значение показывается один раз), назначение тарифов и цен (`price_version++` при смене цены), пополнение/корректировка, журнал, заказы с провайдерскими данными, `cancel` / `reconcile` / `refund`.
- [ ] Тесты: без ключа/с чужим ключом → 401; закупочный ключ компании не открывает `/b2b-admin/*`; смена цены повышает версию, повтор той же цены — нет.

### Task A4: Закупочное API (`/b2b/*`) и заказы
**Files:** Create `src/modules/b2b/purchase/*` (`ResellerKeyGuard`, `B2bOrdersService`, DTO).
**Produces:** `GET /b2b/tariffs`, `GET /b2b/balance`, `POST /b2b/orders {client_order_id, tariff_id, price_version}` → 202, `GET /b2b/orders`, `GET /b2b/orders/:client_order_id` (поддерживает `?updated_since=` для синхронизации).
- [ ] Тесты: идемпотентность (тот же запрос → тот же заказ; другая версия цены/тариф → 409); устаревшая версия → 409 `PRICE_CHANGED`; недоступный тариф → 422; заблокированная компания → 403 на покупку, 200 на чтение; чужой заказ → 404; один резерв на заказ.

### Task A5: Выпуск и сверка
**Files:** Create `src/modules/b2b/issuance/*`; Modify `src/modules/order/create-sim/create-sim.service.ts` (только вынос общего), `src/http/*.gateway.ts` (типизированные ошибки с `status`/`body`).
**Produces:** `B2bIssuanceService.submit(resellerOrderId)` (атомарный claim `RESERVED→SUBMITTING`, создание `Sims`, вызов поставщика, классификация исхода, проактивный запрос JoyTel), `B2bSettlementService` (cron 10 с: `SUBMITTED→ISSUED` + `capture`, `FAILED` + `release`; `SUBMITTING` старше 5 мин → `RECONCILE`).
- [ ] Тесты: таймаут → `RECONCILE`, резерв удержан, провайдер вызван 1 раз; ответ-отказ → `FAILED`, резерв освобождён один раз; повторный callback → один `capture`; `cancel` во время `SUBMITTING` невозможен; `reconcile(FAILED|ISSUED)` и `refund` пишут ровно одну проводку.

### Task A6: eSIM, QR, расход
**Produces:** `GET /b2b/orders/:id/esim` (ICCID, activation_code, инструкции), `…/qr` (PNG на лету), `…/usage` (живой запрос поставщика через существующий код).

### Task A7: Изоляция розницы
